## Context

当前 Trader 2.2/2.3 是一个 A 股交易决策辅助系统，以 Hermes skill 形式输出标准化 Markdown 报告。开发者的日常工作流是：

1. 运行 skill（如 `trader script --target <NAME>`）
2. 观察输出内容（微信端渲染、数据准确性、分析逻辑）
3. 发现问题后直接修改代码
4. 再次运行验证

这个流程的问题在于：改动缺乏记录，容易重复踩坑；性能问题和数据问题混在一起处理，缺乏分类；没有标准化的「改之前/改之后」对比机制。

## Goals / Non-Goals

**Goals:**
- 定义 skill 输出迭代的标准流程，让每次改动有 proposal 可追溯
- 提供四类变更（性能/数据/功能/显示）的快速模板，降低提案成本
- 在复盘循环中集成输出质量检查

**Non-Goals:**
- 不改变现有 Hermes skill 的运行方式
- 不引入额外的 CI/CD 或部署流程
- 不做自动化的输出质量评分（人工判断为主）

## Decisions

### 1. 变更分类为四类

**决定**: 将所有 skill 输出相关变更分为四类：性能优化、数据修复、功能增改、显示调整。

**理由**: 这四类覆盖了开发者 90%+ 的日常迭代场景，每类有不同的诊断路径和验证方式。性能问题需要 profiling，数据问题需要对比源数据，功能问题需要逻辑验证，显示问题需要微信端截图对比。

**替代方案**: 不分类直接走通用流程 → 容易遗漏关键检查项。

### 2. 使用 OpenSpec 作为变更管理工具

**决定**: 复用项目已有的 OpenSpec 基础设施，不引入新工具。

**理由**: OpenSpec 已集成在项目中，proposal → design → tasks 链路成熟，且与 AI agent 协同友好。

### 3. 轻量级模板而非严格流程

**决定**: 提供模板但不强制完整走完 proposal → design → specs → tasks 全链路。小改动（如改一个显示字段）可以只写 proposal + 直接改。

**理由**: 过于严格的流程会降低迭代速度，与「看到问题就改」的开发习惯冲突。模板的价值在于引导思考，而非增加摩擦。

## Risks / Trade-offs

- [风险] 开发者嫌麻烦跳过提案 → 缓解：提供极简模板，1 分钟内可完成
- [风险] 变更记录堆积但没人看 → 缓解：在复盘流程中加入变更回顾环节
- [风险] 四类分类不够用 → 缓解：允许「其他」类别，未来按需扩展
