## Context

当前体系对主力资金的处理散落在多个模块中：big_order.py 做大单检测（启发式推断）、wyckoff_core.py 通过 Spring/Upthrust 隐含识别主力行为、chip_distribution.py 追踪筹码分布。但没有一个模块把"主力在干什么"当作连续的生命周期来跟踪，也没有一个明确的信号输出"当前主力处于什么阶段"。

现有融合层（fusion_core.py）有两个环境修正因子：market_env（大盘牛熊）和 hmm_regime（HMM前瞻状态）。主力行为可以作为第三个环境因子，形成"三重滤镜"架构。

数据来源方面，东方财富API提供个股日线级资金流向数据（按单笔金额分超大单/大单/中单/小单），extend_data.py 已有直连东方财富API的模式可复用。

## Goals / Non-Goals

**Goals:**
- 新增日线级资金流向数据采集，通过东方财富HTTP API直连（不依赖akshare，避免代理问题）
- 实现主力行为五阶段识别（吸筹/试盘/拉升/派发/砸盘），输出阶段+置信度
- 将主力行为作为环境因子接入 fusion_core.py，调节融合权重（不做硬门控）
- 复盘面板新增「主力行为」段落
- 资金流向数据纳入现有缓存体系

**Non-Goals:**
- 不做入池硬门控（推测数据不适合一票否决）
- 不做T0盘中实时主力异动告警（日线级数据时效性不够）
- 不接入Level2数据或龙虎榜（超出免费数据范围）
- 不修改 stage_positioning.py（避免耦合）
- 不修改信号契约主体结构（仅在 extras 中轻量附加）

## Decisions

### Decision 1: 数据源选择 — 直连东方财富HTTP API

**选择**: 直接调用东方财富 push2his.eastmoney.com API，不通过 akshare 封装。

**原因**:
- akshare 在当前环境有代理问题（push2.eastmoney.com 被代理拦截）
- extend_data.py 已有直连东方财富 datacenter API 的成功模式（`_http_get_json` 辅助函数）
- 直连减少中间层依赖，调试更直接

**替代方案**:
- akshare `stock_individual_fund_flow()`：封装好但代理不稳定
- 新浪/腾讯资金流向API：数据粒度不够（无超大单/大单分类）

**API 端点**:
```
GET https://push2his.eastmoney.com/api/qt/stock/fflow/daykline/get
参数:
  secid: 1.688248 (市场.代码，沪=1，深=0)
  lmt: 0 (返回全部)
  klt: 101 (日线)
  fields1: f1,f2,f3,f7
  fields2: f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61,f62,f63,f64,f65
返回: 每日主力/超大单/大单/中单/小单净流入（万元）
```

### Decision 2: 主力行为阶段模型 — 五阶段 + 规则引擎

**选择**: 基于规则的五阶段分类器，不用机器学习模型。

**原因**:
- 规则可解释，每条规则对应一个可理解的资金行为
- 数据量不足以训练可靠的ML模型（日线级，单票最多300天）
- 规则可以逐步调优，ML模型是黑箱

**五阶段定义**:

| 阶段 | 价格特征 | 资金特征 | 筹码特征 |
|------|----------|----------|----------|
| 吸筹 (accumulation) | 横盘或缓跌 | 缓慢净流入 | 集中度上升 |
| 试盘 (testing) | 单日脉冲上涨后回落 | 单日大额净流入后回流 | 无明显变化 |
| 拉升 (markup) | 量价齐升 | 连续净流入+加速 | 集中度高 |
| 派发 (distribution) | 高位滞涨 | 净流出或流入萎缩 | 松散化 |
| 砸盘 (markdown) | 放量下跌 | 连续大额净流出 | 恐慌松散 |

**输出结构**:
```python
{
    "stage": "accumulation",       # 阶段名称
    "confidence": 0.6,             # 置信度 0-1
    "cum_flow_5d_wan": 3200,       # 5日累计净流入（万元）
    "cum_flow_10d_wan": 4500,      # 10日累计净流入
    "consecutive_inflow_days": 3,  # 连续流入天数
    "net_flow_pct": 0.08,          # 净流入占成交额比
    "flow_price_relation": "价跌资入",  # 价资关系描述
    "signals": ["连续3日净流入", "筹码集中度上升"],
}
```

### Decision 3: 融合层集成 — 权重修正，不新增信号维度

**选择**: main_force_env 作为环境修正因子，在 Scenario Priority Filter 之后、weighted_score 计算之前，对三路信号的权重做微调。

**原因**:
- 主力行为不是独立于价格/量的第四路信号，它已经隐含在 Wyckoff/Volume Profile 中
- 做成第四路信号会导致重复计算（Spring 本身就是识别主力承接）
- 环境修正因子与 market_env/hmm_regime 形成对称架构，改动最小

**权重调节规则**:

| main_force_env | 缠论权重修正 | 威科夫权重修正 | 动量权重修正 |
|----------------|-------------|---------------|-------------|
| accumulation   | 不变        | +10%          | -10%        |
| testing        | 不变        | 不变          | 不变        |
| markup         | -5%         | 不变          | +10%        |
| distribution   | -10%        | +10%          | -5%         |
| markdown       | -15%        | -10%          | -10%        |
| unknown        | 不变        | 不变          | 不变        |

调节后重新归一化，确保三路权重之和为 1.0。

### Decision 4: 缓存策略 — fund_flow/ 子目录，TTL 24h

**选择**: 新增 `~/.trader/cache/fund_flow/` 子目录，TTL 86400秒（24小时），集成到 `warm_pool_cache()`。

**原因**:
- 资金流向数据日线级，每日收盘后更新一次，TTL 与 daily 一致
- 盘后预缓存次日复盘/分析直接读缓存，避免每次调API
- 与现有缓存管理命令（cache warm/clear）兼容

**缓存结构**: 每个股票一个 JSON 文件，包含近30日原始数据+计算后的特征。

### Decision 5: 复盘输出 — 新增「主力行为」段落

**位置**: 插在「分时走势与大单回溯」和「五层打分」之间。

**内容**:
- 行为阶段 + 置信度
- 近5日/10日累计净流入
- 今日净流入
- 价资关系判断
- 近5日趋势符号（↑↓箭头序列）
- 关键提示（如"连续N日净流入，关注放量突破"）

**格式约束**: 遵守微信端纯文本规范，不使用 Markdown 标题/表格/粗体。

## Risks / Trade-offs

**[数据精度]** 资金流向是按单笔金额推算的主力/散户分类，不是真实Level2机构持仓。
→ 缓解: 作为展示层和软权重，不做硬门控。用户可选择忽略。

**[API稳定性]** 东方财富API可能因网络/代理问题不可用。
→ 缓解: 缓存机制减少调用频率。API失败时返回 unknown 阶段，不影响其他模块。复用 extend_data.py 的 `_http_get_json` 模式，自带超时和异常处理。

**[规则调优]** 五阶段的阈值（连续天数、净流入比例等）需要根据实际数据调优。
→ 缓解: 阈值集中配置，方便调整。初期保守设置，宁可漏报不误报。

**[重复计算]** 主力行为与 Wyckoff Spring/Upthrust 有语义重叠。
→ 缓解: 主力行为是环境修正因子，不新增独立信号维度。调节幅度保守（±10-15%），不会大幅改变原有决策。

## Open Questions

- 东方财富API的 secid 映射：沪=1、深=0，创业板/科创板的市场标识需要验证
- 资金流向数据的时效性：盘后几点更新？是否需要等待？
- 五阶段阈值的初始值需要基于历史数据做一次基准测试
