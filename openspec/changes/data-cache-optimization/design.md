## Context

Trader 2.3 的单票分析流程包含 11 次网络请求，分布在 3 个串行阶段：

```
Phase 1: load_market_snapshot (并行, 4路) — quote/daily/5m/ticks
Phase 2: _enrich_snapshot (并行, 4路) — shareholder/eps/unlocks/theme
Phase 3: market_env.assess (串行) — index quote + index kline + HMM
```

当前没有任何文件级缓存（`cache_utils.py` 只被 `fetch_qfq_daily` 使用，其他模块未接入）。每次分析都重新抓取全部数据。

Hermes 环境下（海外服务器访问国内金融 API），单次分析耗时 5-15 秒，其中 80% 是网络延迟。

## Goals / Non-Goals

**Goals:**
- 盘中分析耗时从 5-15 秒降至 1-3 秒
- 盘后批量操作（排序/作战表/复盘）耗时降低 90%
- 缓存数据准确性与实时抓取完全一致
- 缓存不存在或过期时自动 fallback，行为与当前一致

**Non-Goals:**
- 不改变实时行情（quote）的抓取逻辑（盘中必须实时）
- 不改变 tick 数据的抓取逻辑（盘中必须实时）
- 不引入新的外部依赖（Redis 等）
- 不重构 Provider 架构（那是另一个技术债）

## Decisions

### 1. 日线缓存合并策略：缓存历史 + 追加当日实时

**决策**: 盘中读取日线缓存（不含今天）后，将今天的实时 quote 合并为一根 bar 追加到末尾。

**为什么**: 
- 日线数据收盘后不变，缓存安全
- 但 MA/ATR 计算需要包含今天的 close，否则指标有偏差
- 合并逻辑简单：`cached_bars + [today_bar_from_quote]`

**替代方案**: 
- 完全不缓存日线 → 速度提升有限（只省 0.3-0.8s）
- 缓存含今天的 bar → 盘中数据不准（bar 在交易时间内持续变化）

### 2. 扩展数据缓存 TTL 12 小时

**决策**: 股东户数、机构 EPS、解禁信息、题材归因写入文件缓存，TTL 12 小时。

**为什么**:
- 这些数据日内不会变化（股东户数按季度更新，解禁按计划发布）
- 同花顺题材归因每日更新一次，12 小时 TTL 覆盖一个交易日
- `_enrich_snapshot` 已有 10 分钟内存缓存，但进程重启就丢失

**替代方案**:
- 24 小时 TTL → 可能错过盘后更新（如盘后发布的公告）
- 内存缓存（现状）→ 进程重启丢失，Hermes 上每次冷启动都要重新抓

### 3. 大盘环境缓存 + 追加当日指数

**决策**: 盘后缓存大盘指数的 90 日 K 线和 HMM regime 结果。盘中读缓存后追加当日实时指数价格。

**为什么**:
- `market_env.assess()` 是串行的（在 Phase 1/2 之后），白白多等 1-3 秒
- HMM 计算基于历史日收益率，不含今天的结果完全可用
- 追加今日指数后 MA/HMM 判断更准确

**替代方案**:
- 和 Phase 1 并行 → 仍需抓取，只是省了等待时间
- 不缓存 HMM → 每次重新拟合 Baum-Welch（50-100ms CPU，不值得缓存）

### 4. 写入时校验，不写入脏数据

**决策**: 缓存写入前校验：bar 数量 >= 200、close > 0、日期单调递增。校验失败不写入。

**为什么**:
- API 偶尔返回空数据或异常值，如果写入缓存会污染后续所有读取
- 现有代码没有写入校验，这是新增的风险点

**替代方案**:
- 读取时校验 → 每次读取都要校验，性能开销
- 不校验 → 风险太高

### 5. 盘后预缓存集成到 t0_cron.py

**决策**: 在现有 `t0_cron.py` 的收盘后流程中新增预缓存步骤。

**为什么**:
- `t0_cron.py` 已经有定时任务机制
- 选股池 `~/.trader/pool.json` 已有标准格式
- 不需要新增调度器

**替代方案**:
- 独立脚本 → 增加部署复杂度
- 用户手动触发 → 不可靠

## Risks / Trade-offs

**[缓存污染]** API 返回脏数据写入缓存 → 后续一直读到错误数据
→ 缓解: 写入前校验 bar 数量/价格/日期，失败则不写入

**[停牌股票]** 缓存的日线不含今天，但用户以为今天有交易
→ 缓解: quote 仍然实时抓，通过 volume=0 + change_pct=0 判断停牌

**[磁盘空间]** 10 只股票 × 300 根 bar × 每根 ~200 字节 ≈ 600KB，可忽略
→ 无需特殊处理

**[多进程竞争]** 盘后预缓存和用户手动分析同时写入
→ 缓解: 现有 DataManager 的 fcntl + tmp-rename 机制已覆盖

**[合并逻辑错误]** 缓存 bar 和实时 quote 合并时日期重复或遗漏
→ 缓解: 合并时以日期为 key 去重，今天日期的 bar 用实时 quote 覆盖
